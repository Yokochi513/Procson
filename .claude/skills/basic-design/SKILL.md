# 基本設計書ジェネレーター（仕様駆動方式）

任意の**要件定義書**を入力として受け取り、その内容に忠実な**基本設計書（外部設計書）**を生成するためのスキルです。

このスキルは特定のプロジェクト・技術・ドメインの知識を一切前提としません。入力された要件定義書だけを根拠に設計してください。要件定義書に書かれていないことを「設計判断」として補う場合は、必ずその旨を明示し、可能なら事前にユーザーへ確認します（憶測で仕様を確定させない）。

## 仕様駆動方式とは

この設計書の核は **要件と設計の双方向トレーサビリティ** です。次の2つを常に成立させます。

1. **設計 → 要件**: すべての設計要素は、それが満たす要件（FR-x / NFR-x 等のID）を参照できる。根拠のない設計を作らない。
2. **要件 → 設計**: すべての要件は、設計のどこかで必ずカバーされる。取りこぼし（カバレッジ漏れ）を作らない。

そのため最後に必ず**トレーサビリティマトリクス**を作り、全要件が設計に落ちていることを確認します。要件IDが無い要件定義書の場合は、このスキルの中で機能要件・非機能要件に一意なIDを採番してから設計を始めてください（採番ルールは下記）。

## 手順

### 1. 入力（要件定義書）を読み込む

対象の要件定義書を読み込み、次の観点で要素を抽出する。書かれていない項目は「未記載」として記録する（無理に埋めない）。

- 目的・コンセプト / スコープ（やること・やらないこと）
- 想定ユーザー・利用シーン
- 機能要件（Functional Requirements）
- 非機能要件（性能・セキュリティ・可用性・運用・互換性 等）
- 画面・UI
- システム構成・技術スタック
- データモデル / データ項目
- 外部インターフェース（API・外部システム連携）
- 制約・前提
- 受け入れ基準（完成の定義）

### 2. 要件にIDを採番する（IDが無い場合のみ）

トレーサビリティの前提として、各要件に一意なIDを与える。

- 機能要件: `FR-1`, `FR-2`, ...
- 非機能要件: `NFR-1`, `NFR-2`, ...
- 制約: `CON-1`, ...（必要に応じて）

要件定義書側に既にID（例: `FR-3`）があればそれをそのまま使う。採番した場合は、設計書の文書情報セクションで「本設計書で採番した」旨を明記する。

### 3. 不明点・ギャップを洗い出して確認する

設計を確定させる前に、要件定義書だけでは設計を一意に決められない箇所を洗い出す。例:

- 技術スタックが未指定 / 複数候補ある
- データ項目の型・必須/任意・桁・制約が不明
- エラー時の振る舞い、境界値、上限値が未定義
- 画面遷移・状態遷移の分岐が曖昧
- 外部APIの認証方式・レート制限・タイムアウト方針が未記載

重要な分岐は `AskUserQuestion` で確認する。確認できない／軽微なものは、設計書の「未決事項・前提・課題」セクションに前提として明記したうえで、最も妥当なデフォルトで設計を進める（必ず「これは設計上の前提である」と分かるように書く）。

### 4. 基本設計書を生成する

`references/design-template.md` のテンプレートに従って設計書を作成する。**テンプレートを読み込んでから**書き始めること。

- 各設計セクションでは、対応する要件IDを明記する（例: 見出し脇や表の「対応要件」列に `FR-1, FR-3`）。
- 入力に存在しないセクション（例: 画面が無いバックエンドのみのシステムなら画面設計）は「該当なし」と書くか、省略する。要件に無いセクションを無理に創作しない。
- 図はテキスト（コードブロック内のASCII図 / Mermaid）で表現してよい。
- 表現は「実装者が迷わず作れる」粒度を目指す。ただし詳細設計（クラス内部実装・関数シグネチャ）まで踏み込みすぎない。基本設計は「何を・どういう構造で作るか」のレイヤー。

### 5. カバレッジを検証する

設計書末尾のトレーサビリティマトリクスで、抽出した全要件IDが「対応する設計箇所」を持つか確認する。

- カバーされていない要件があれば、設計に追記するか、対応できない理由を「未決事項」に記録する。
- 逆に、どの要件にも紐づかない設計要素があれば、それは過剰設計の疑い。要件由来でないなら理由を明記する。

### 6. 出力する

設計書は要件定義書と同じ場所に、分かりやすいファイル名（例: `基本設計_<システム名>.md`）で出力する。ファイル名・出力先はユーザーに合わせる。生成後、カバレッジ結果（全X件中Y件カバー、未決Z件）を簡潔に報告する。

## 設計を書くときの原則

- **検証可能に書く**: 「速くする」ではなく「1往復あたり通常3秒以内（外部API応答時間に依存）」のように、後でテストで確認できる形にする。受け入れ基準があるなら、それを満たせる設計になっているか意識する。
- **要件を超えない**: スコープ外（要件定義書の「やらないこと」）の機能を設計に持ち込まない。将来拡張は「将来拡張」として別枠に書く。
- **前提は可視化する**: 要件に無い判断は必ず前提として明示する。サイレントに仕様を足さない。
- **入力の構造を尊重する**: 要件定義書の章立て・用語・ID体系がある場合はそれに合わせると、読み手（要件定義書の作者）が対応を追いやすい。

詳細なセクション構成と各セクションの書き方は `references/design-template.md` を参照すること。
