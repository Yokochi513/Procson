# スライドひな型（Marp Markdown）

このファイルは `present-me` スキルが発表資料を生成するときのひな型です。**フェーズ2で合意したアウトラインに沿って**このひな型を埋める。すべての章を必ず使う必要はなく、発表の目的・持ち時間に合わせて取捨選択する（発表に不要な章は省く。無理に埋めない）。

## 全体の作法

- スライド区切りは `---`（前後に空行）。
- 各スライドは **1メッセージ**。タイトル（`#` 見出し）はそのスライドの主張そのものにする。
- スライドに書くのは要点だけ。話す内容は発表者ノート（`<!-- ここに話すことをメモ -->`）に書く。
- 図は Mermaid かコードブロック内 ASCII で表現してよい。

## frontmatter（先頭に置く）

```markdown
---
marp: true
paginate: true
title: <発表タイトル>
---
```

## 標準構成（この順で、必要な章だけ使う）

### 1. タイトルスライド
- 発表タイトル（＝核メッセージを想起させるもの）、発表者、日付、場。

### 2. 聴衆の関心・課題への接続（つかみ）
- 聴衆が今困っていること／関心事を1枚で示し、「だからこの話をする」と橋を架ける。
- いきなり技術詳細や結論の前に、なぜこの話を聞く価値があるかを示す。

### 3. 結論（核メッセージ）
- フェーズ1で決めた**1文の核メッセージ**を1枚で提示。
- 「今日持ち帰ってほしいのはこれ1つ」を明示する（先出しすると聴衆が聞く姿勢を作れる）。

### 4. アジェンダ（任意・長めの発表のみ）
- 章立て。5分以下のLTなら省略可。

### 5. 本論（章ごと）
各章は「主張スライド → 根拠スライド」の組で構成する。
- **主張スライド**：その章で言いたいこと1つ。タイトル＝主張。
- **根拠スライド**：データ・図・デモ・事実で裏づける。1枚に詰め込みすぎない。

### 6. まとめ（核メッセージの再提示）
- 3で出した核メッセージをもう一度。本論を踏まえて言い換える。
- 「結局この1つ」を再確認する。

### 7. ネクストアクション / お願い
- 目的が「行動/承認」なら、聴衆に具体的に何をしてほしいかを1枚で示す。

### 8. 補足（Appendix・任意）
- 想定質問への回答、詳細データ、参考リンク。本編では出さず質疑用に置く。

## スライド記述例

```markdown
---
marp: true
paginate: true
title: 就活提案エージェントの紹介
---

# 就活を「探す」から「提案される」へ

2026-07-15 / チーム定例
発表者：〇〇

<!-- 15分。聴衆はチームメンバー（本プロダクトは既知、今日は設計判断の共有が目的）。 -->

---

# 学生は「求人が多すぎて選べない」で止まっている

- 求人検索は充実したが、選定は本人任せ
- 「自分に合うか」を判断する材料が不足

<!-- 聴衆の共通課題に接続。数字があればここで出す。 -->

---

# 結論：条件入力から「提案＋根拠」まで自動化する

今日の持ち帰り：**エージェントが提案理由まで出すことで選定の負荷を下げる**

<!-- 核メッセージを先出し。以降のスライドはすべてこれを裏づける。 -->

---

# 提案は3段階のパイプラインで生成する

```
入力 → マッチング → 根拠生成 → 提案
```

<!-- 図は Mermaid でも可。1枚1メッセージを守る。 -->

---

# まとめ：選ぶのではなく「選ばされる」体験にする

- 課題：選定負荷が高い
- 解決：提案＋根拠の自動生成
- 効果：意思決定の時間短縮
```

## 自己点検チェックリスト（生成後に確認）

- [ ] すべてのスライドが核メッセージ（1文）に奉仕しているか。しないスライドは削ったか。
- [ ] 1スライド=1メッセージになっているか。タイトルが主張になっているか。
- [ ] 文字で埋まっていないか。詳細は発表者ノートに逃がしたか。
- [ ] 主張に根拠（データ/図/事実）が添えられているか。憶測を断定していないか。
- [ ] 枚数が持ち時間に見合うか（口頭発表の目安：1枚1〜2分）。
- [ ]（評価観点がある場合）全評価観点（EV-x）に対応するスライドがあり、配点の大きい観点が厚く扱われているか。カバレッジ表で確認したか。
