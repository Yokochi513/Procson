# 発表資料ジェネレーター（ヒアリング駆動方式）

発表資料（スライド）を、いきなり書き始めずに **[[grill-me]] のように一問一答で徹底ヒアリングして合意形成してから** 作成するためのスキルです。

発表資料は「情報を並べたもの」ではなく「聴衆をある状態から別の状態へ動かすための道具」です。目的・聴衆・核メッセージが曖昧なまま作ると、きれいだが刺さらない資料になります。このスキルは、まず**発表の設計（何を・誰に・どう伝えて・どう動かすか）を決定木として1つずつ潰し**、合意できてからスライドに落とします。

## 基本方針（grill-me 由来）

1. **一問一答**：質問は**一度に1つ**。まとめて質問攻めにしない。分岐（前の答えで次の質問が変わる）を1つずつ解決していく。
2. **常に推奨案を添える**：各質問には「あなたのおすすめは？」の答え（推奨案とその理由）を必ず提示する。ユーザーは選ぶ／却下するだけで前に進める。
3. **資料で分かることは訊かない**：既存資料（要件定義書・基本設計書・議事録・README・コード・過去スライド等）で答えられることは、質問せずに自分で読んで埋める。訊いてよいのは「本人の意図・優先順位・聴衆事情」など資料に無いことだけ。
4. **合意してから書く**：発表設計（下記フェーズ1）がユーザーと合意できるまでスライド本文を書き始めない。憶測で構成を確定させない。

## 手順

### フェーズ0：入力を集める

- ネタ元になる資料（設計書・議事録・コード・データ・既存スライド等）があれば場所を確認して読み込む。
- 発表の外形が分かる材料（持ち時間・場・形式指定）があれば拾う。
- ここで分かったことは以降のヒアリングで**質問しない**（読めば分かることは訊かない、の原則）。

### フェーズ1：発表設計をヒアリングで詰める（1問ずつ）

以下の決定木を上から順に、**1問ずつ・推奨案つき**で潰していく。前の答えで後段が変わるので、順番を守る。重要な分岐は `AskUserQuestion`、細かい確認は通常の質問でよい。

1. **目的（ゴール）**：この発表で聴衆に最終的に何をしてほしいか。「知ってほしい／納得してほしい／承認してほしい／行動してほしい」のどれか。1つに絞る。
2. **聴衆**：誰が聞くか。前提知識のレベル、立場（決裁者／同僚／初学者）、聴衆が今抱いている疑問・関心。
3. **核メッセージ（1文）**：この発表を1文に要約すると何か。聴衆が終了後に1つだけ持ち帰るなら何か。以降すべてのスライドはこの1文に奉仕する。
4. **外形の制約**：持ち時間、想定枚数、発表形式（口頭+スライド／読む資料／LT等）、指定フォーマットの有無。
5. **ストーリー構成**：核メッセージを伝える筋道を選ぶ。（例：課題→原因→解決策→効果／時系列／PREP／Before-After）。まず**アウトライン（章立て）**として提示し、合意を取る。
6. **各章の主張と根拠**：章ごとに「言いたいこと1つ」と「その裏づけ（データ・図・デモ・事実）」を確定。根拠が資料にあるなら参照、無いなら本人に確認。
7. **形式・出力**：出力フォーマットとファイル形式を決める（下記「出力形式」）。デザインの濃さ（社内共有レベル／清書レベル）も確認。

各フェーズで得た合意は忘れないよう簡潔にメモ（箇条書き）し、フェーズ2の直前に**発表設計サマリ**として一度提示して最終合意を取る。

### フェーズ2：アウトラインを合意する

スライド本文の前に、**1スライド=1メッセージ**の原則でアウトライン（スライドタイトルの列＋各スライドの主張1行）を提示し、合意を取る。ここで枚数・順序・過不足を調整する。細部の作文はまだしない。

### フェーズ3：発表資料を生成する

`references/slide-template.md` を読み込んでから、合意済みアウトラインに沿ってスライドを書く。作成原則（下記）を守る。

### フェーズ4：出力・自己点検

- ネタ元と同じ場所に分かりやすいファイル名（例：`発表資料_<テーマ>.md`）で出力する。
- 生成後、「核メッセージがブレていないか」「各スライドが1メッセージか」「持ち時間に対して枚数は妥当か（口頭発表の目安：1枚あたり1〜2分）」を自己点検し、結果を簡潔に報告する。

## 出力形式

指定が無ければ **Marp 形式の Markdown**（`---` でスライド区切り、先頭に `marp: true` の frontmatter）を既定とする。Markdown なのでこのリポジトリの他資料と同じように差分管理でき、必要なら Marp で PDF/HTML/PPTX に書き出せる。ユーザーが PowerPoint・Google スライド・プレーンな Markdown 等を希望すればそれに合わせる。

## 作成原則

- **1スライド=1メッセージ**：1枚で言いたいことは1つ。タイトルはその主張そのもの（「アーキテクチャ」ではなく「認証はAPI Gateway一箇所に集約する」のように、体言止め＋主張）。
- **核メッセージに奉仕させる**：フェーズ1で決めた1文に貢献しないスライドは削る。「入れたいから入れる」をしない。
- **箇条書きは主張、詳細は口頭/ノート**：スライドは要点だけ。細かい説明は発表者ノート（Marp なら `<!-- -->` のコメント）に回し、スライドを文字で埋めない。
- **主張には根拠を添える**：数値・図・デモ・事実で裏づける。裏づけられない主張はトーンダウンするか落とす。憶測を断定で書かない。
- **図はテキストで表現してよい**：構成図・フローは Mermaid かコードブロック内の ASCII 図で書く。
- **聴衆の既知から始める**：最初のスライドで聴衆の関心・課題に接続してから本題へ入る（いきなり結論の技術詳細に飛ばない）。

詳細なスライド構成とひな型は `references/slide-template.md` を参照すること。
